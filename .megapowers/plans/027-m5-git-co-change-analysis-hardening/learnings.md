# Learnings: 027-m5-git-co-change-analysis-hardening

- **Sentinel keys in shared tables need filtering at every read site.** Storing the git HEAD key in `file_hashes` was pragmatic (reuses existing infrastructure), but `getStatistics()` queried that table without filtering `__`-prefixed entries, causing `files.total` to be inflated by 1 and `files.stale` to always have a false positive (the sentinel path doesn't exist on disk). The fix is a one-liner filter, but it required a bug-finding step in code review. The cleanup loop in `pipeline.ts` correctly had the `startsWith("__")` guard; the statistics query was the gap. Pattern: whenever a sentinel is written to a data table, audit *all* read paths for the same table.

- **`tree-sitter` field names for import specifiers are asymmetric.** For `import { foo as bar }`, the `name` field on the `import_specifier` node is `foo` (the exported/original name) and `alias` is `bar` (the local binding). This is the correct mapping for building edges — we want the original name for cross-module resolution — but it's counterintuitive at first glance (you might expect `name` to be the local name). The field name `alias` makes more sense once you see it. For `export { foo as baz }`, the same pattern applies on `export_specifier`.

- **`walk` visits children even when the visitor returns early.** The `walk(node, visit)` function calls `visit(n)` then recurses into `n.namedChildren` regardless of the visitor's return value. This means an early `return` in the visitor only skips the rest of *that* visitor invocation — it doesn't prevent children from being visited. This is the correct behavior for processing re-exports (`export_statement` handler returns early, but child nodes are still visited if walk continues). Worth noting explicitly in code or comments so future contributors don't add a guard thinking they're preventing double-processing.

- **Dynamic imports appear as `call_expression` nodes with `fn.type === "import"` in tree-sitter.** The tree-sitter TypeScript grammar treats `import("./mod")` as a call expression where the `function` field is an `import` keyword node (not an identifier). This is easy to handle once you know it, but non-obvious to discover without inspecting the CST. The distinction from `import_statement` (which has a dedicated node type) matters because dynamic imports can appear anywhere in the AST, not just at the top level.

- **Deduplication key scope matters.** The `pushEdge` key was extended to include `evidence`, which prevents over-deduplication when the same (source, target, kind, provenance) pair has legitimately different evidence strings. However, this creates a subtle discrepancy: the in-memory `edges` array from `extractFile` can contain edges that SQLite's `INSERT OR REPLACE` will collapse (last-write-wins on the PK). Tests that assert on `extractFile` return values directly will see more edges than what's persisted. For now this is fine, but if a test counts edges precisely it should account for this.

- **Exponential decay with `halfLifeDays = windowDays / 4` is a reasonable default.** For a 365-day window, the half-life is ~91 days — commits from 3 months ago contribute half as much as today's commits. This means very old history (>1 year) is effectively noise-suppressed. The confidence cap at 0.9 (not 1.0) intentionally leaves room for LSP and agent edges to score higher, preserving the provenance hierarchy.

- **Code review found the sentinel stats bug that tests missed.** All 19 acceptance criteria passed verification, but the code review's manual script (`bun run stats-bug-test.ts`) revealed `files.total: 3, files.stale: 3` for a 2-file repo. The staleness tests used fresh stores (no git HEAD key present), so they didn't expose it. Lesson: for features that interact across phases (git stage writes sentinel; statistics reads it), end-to-end integration tests covering the *combined* behavior are more valuable than unit tests covering each phase independently.
