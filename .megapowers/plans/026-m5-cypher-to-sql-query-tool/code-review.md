## Strengths

- **Clean three-layer separation**: parser (`graph-query-parser.ts`), compiler (`graph-query-compiler.ts`), renderer (`graph-query-render.ts`) are independently testable and each has targeted tests. This is the right architecture for a feature with complex validation requirements.

- **Parameterized SQL throughout** (`compiler.ts` lines 69–101): Values never appear in SQL text. The compiler test (`test/graph-query-compiler.test.ts` lines 21–22) explicitly asserts `not.toContain("foo")` and `not.toContain("bar")` to prove this.

- **SELECT-only guard on `queryRows`** (`sqlite.ts` lines 228–230): Even though all SQL is generated by the compiler, the runtime rejects non-SELECT statements. Good defense-in-depth.

- **Well-scoped `effectiveEdgeAliases`** (`compiler.ts` line 91): When the edge has no alias, the compiler uses an empty map for projections, which prevents the edge row from being included in output without a named alias — consistent with the spec.

- **Stale detection composes correctly**: `renderGraphQueryRows` calls `computeAnchor` from the existing output layer (`render.ts` line 42), keeping the stale-detection logic in one place and reusing the existing hash-comparison logic.

- **Test isolation**: End-to-end tests create per-test temp dirs and clean them up in `finally` blocks, preventing flaky cross-test interference.

## Findings

### Critical

### Important

**Bug 1 (fixed): Mutation keyword false positive in string literals**
- **File**: `src/tools/graph-query-parser.ts` line 137 (pre-fix)
- **What**: `rejectUnsupported` ran `/\bCREATE\b|\bMERGE\b|\bDELETE\b|\bSET\b/i` against the raw query string, including quoted values. `MATCH (a {name: "create"}) RETURN a` was rejected with `unsupported_error: mutating queries are not supported` — a valid read-only query.
- **Why it matters**: Agents querying for real functions named "create", "delete", "merge", or "set" (common in codebases) would get a surprising and misleading error.
- **Fix applied**: Strip double-quoted string literals before applying mutation keyword checks. Added `const queryWithoutStrings = query.replace(/"[^"]*"/g, '""')` and applied the regex to `queryWithoutStrings` instead. Test added: `test/graph-query-parser-mutation-string-literal.test.ts`.

**Bug 2 (fixed): WHERE predicates do not validate alias binding**
- **File**: `src/tools/graph-query-parser.ts` lines 219/231 (pre-fix)
- **What**: `parseWhere` parsed alias/property/value triples but did not check that the alias was declared in MATCH. An unbound WHERE alias (e.g., `WHERE z.name = "foo"` where `z` is not in MATCH) passed parsing silently. The compiler then read `nodeAliases["z"]` → `undefined` and emitted SQL `undefined.name = ?`. SQLite rejected this, producing `execution_error` instead of `validation_error`.
- **Why it matters**: Criterion 25 says unbound aliases must return `validation_error`. Returning `execution_error` is misleading — agents would have no indication the alias was the problem.
- **Fix applied**: In both the traversal branch and the node-only branch of `parseGraphQuery`, call `parseWhere` into a local variable, then iterate predicates and throw `validation_error` for any alias not in `nodeAliases ∪ edgeAliases`. Test added: `test/graph-query-parser-where-unbound-alias.test.ts`.

### Minor

**Dead key in `edgeAliases` when edge has no alias**
- **File**: `src/tools/graph-query-compiler.ts` line 61
- `edgeAliases[ast.match.edge.alias ?? "_edge"] = "e0"` — the fallback key `"_edge"` is stored but never read because `effectiveEdgeAliases` (line 91) is set to `{}` when there's no edge alias. The `"_edge"` entry is unreachable dead code.
- No correctness impact; just a small clarity issue. Could be `if (ast.match.edge.alias) edgeAliases[ast.match.edge.alias] = "e0"` to make the intent explicit.

**`Object.entries` filter ordering**
- **File**: `src/tools/graph-query-compiler.ts` lines 68–71
- Param order for inline node filters depends on insertion order in the parsed filter object, which mirrors the order in the user's query string (`{kind: "f", name: "x"}` vs `{name: "x", kind: "f"}`). The compiler test hardcodes one ordering. Not a bug in practice (the SQL `WHERE` is evaluated as a conjunction regardless of order), but worth noting if the test ordering is relied on for exact equality.

**WHERE property access is unrestricted**
- **File**: `src/tools/graph-query-parser.ts` `parseWhere` (line 145)
- WHERE predicates can reference any column name, including internal ones like `content_hash` or `id`. This is consistent with the spec (no restriction stated) and may be intentional. If the intent is to restrict WHERE to the same allowed properties as inline filters (`kind`, `name`), a validation step would need to be added. Leave for now — not a spec violation.

## Recommendations

1. **Clarify the dead `_edge` key** in compiler.ts line 61. Change to `if (ast.match.edge.alias) edgeAliases[ast.match.edge.alias] = "e0"` for clarity.
2. **Consider a WHERE property allowlist** if agents discover they can probe internal columns. The spec is currently silent on this.
